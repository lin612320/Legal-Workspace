## 一、文档目的

本文档回答三个问题：

1. 现有「律政工作台」距赛题要求的**自主智能体（数字员工）**差在哪（逐条对照评分标准）；
2. 如何用**最小改动**把它升级为"能自主规划、调用工具、交付可验收成果"的智能体应用；
3. 每一阶段做什么、做到什么程度算完成（验收口径），以及对应提升哪个评分维度。

**结论先行**：产品现状是"AI 增强的法律工具箱 + 对话式 RAG 助手"，赛道要求的是"任务理解 → 自主规划 → 工具调用 → 结果交付"的端到端智能体。差的不是底层能力（法库、SQLite、流式对话、悬浮球、Excel/ETL 均已就绪），而是**没有 Agent 循环、没有可验收交付物、没有端到端叙事**。按本文档 P0 → P3 实施后，预计五维总分可从约 58 分提升至 80 分以上。

## 二、参赛背景与定位差距

### 2.1 赛题要求 vs 产品现状（对照）

| 赛题关键词 | 现有产品实际形态 | 差距 |
| --- | --- | --- |
| 任务理解与自主规划 | 用户手动选择模式（通用 / 审合同 / 审质证）后逐条提问 | 无"模糊意图 → 结构化任务 → 分步计划" |
| 工具调用与环境交互 | 全部由**用户手点按钮**触发（检索、翻译、导入、导出） | 无模型自主 function calling 循环 |
| 结果交付与可验收性 | 成果止于聊天文本；模板为 `____` 占位 txt | 无 docx/xlsx 等可验收交付物、无自查校验 |
| 端到端闭环 | 每个版块是独立单点能力 | 无"一次输入 → 完整成果"的闭环 |
| 检索增强 / 记忆 / 工作流 / 多智能体 | 仅对话内 RAG（关键词 top4 注入）、会话持久化 | 无长期记忆、无任务状态机、无多角色编排 |

### 2.2 一句话定位调整

**改前**：法律人的本地 AI 助手（工具箱）。

**改后**（参赛口径）：**可交付法律文书的本地化"办案数字员工"** —— 把"15 万条真实法条 + 大模型 + 工具调用"串成端到端工作流：听懂任务 → 制定计划 → 自主查法条、起草、审查 → 交付可溯源、可打开的《法律文书/审查意见书》，全程数据留在本机。

## 五、总体路线（依赖关系）

```
P0  端到端闭环（合同审查数字员工）        ← 必须最先完成，赛道维度的命根
 │    依赖：现有 laws_search / chat 流式 / 打包流程
 ▼
P1  Agent 骨架：工具调用循环 + 任务状态机 + 流水线模板
 │    依赖：P0 打通的第一条流水线
 ▼
P2  记忆与检索增强：FTS5 / 向量记忆 / 悬浮球任务入口
 │    依赖：P1 的会话与任务落库
 ▼
P3  多智能体协同（可选冲刺）：检索/起草/质检三 Agent
     依赖：P2 的检索与交付底座
```

原则（贯穿全程）：

1. **最小闭环优先**：先让"一条输入 → 一个可打开交付物"跑通，再补边角；
2. **真调用而非摆样子**：演示中模型必须自主连续调用 ≥3 次工具；
3. **人在环上**：计划卡可编辑、每步可人工确认——既是法律场景的负责任设计，也是评委提问"幻觉怎么办"的标准答案；
4. **交付可验收**：产出落盘为 .docx / .xlsx，能双击打开、能被引用溯源核对。

## 六、P0：跑通一条端到端闭环（合同审查数字员工）

### 6.1 主场景与用户旅程

主场景：**律师/法务粘贴一份合同 → 数字员工交付《合同审查意见书.docx》**。

| 步骤 | 用户看到 | 背后发生 |
| --- | --- | --- |
| 1 | 粘贴合同文本，点"一键审查" | 触发任务创建 |
| 2 | 计划卡：条款清单、风险维度、计划检索关键词 | 大模型输出结构化任务 JSON（可编辑） |
| 3 | 进度条逐条"执行中 / 完成" | Agent 循环：自主调用工具 |
| 4 | 预览《审查意见书》（网页/内置预览） | 大模型按模板合成，引用真实法条 |
| 5 | 点"导出 docx / 存入最近文书" | 生成交付物、落 `documents` 表 |
| 6 | 意见书中每处引用带"法条号 + 来源" | 引用溯源（可人工核对，防幻觉） |

### 6.2 任务理解与计划卡（结构化输出）

- 新入口（可在 AI 助手版块顶部加"任务模式"卡片，或新增独立版块"智能体/任务"）：
  1. 用户输入模糊意图（"帮我审一下这份合作协议，重点看违约责任和知识产权"）；
  2. 模型以 JSON Schema 输出：`{ title, intent, clauses[]或分块[], risk_dimensions[], search_keywords[], steps[] }`；
  3. UI 渲染为**计划卡**，允许增删步骤、修改关键词，点"开始执行"才进入 Agent 循环。
- 代码落点：
  - 复用 `src/lib/ai.ts` 的 `chatStream`，新增一次"非流式结构化调用"（或复用流式 + 尾包 JSON 提取），解析 `system` 提示 + `response_format: json_object`（OpenAI 兼容网关普遍支持）；
  - 新增 `src/lib/agent.ts`：任务状态类型、计划卡状态（`planned → running → done / need_confirm`）；
  - 后端新增 `tasks` 相关命令（可先落 `chat_messages` 同款 JSON 方案，正式做法见 §7）。

### 6.3 工具调用循环（本方案关键改动）

目标：把"用户点按钮"改为"**模型发 tool_calls → 前端/后端执行 → 结果回填 → 模型继续**"，直到输出最终答案。

- 前端实现（改动小、演示直观）：
  1. `src/lib/ai.ts` 的请求体增加 `tools` 数组（OpenAI 兼容 tools 协议），并解析 `choices[0].message.tool_calls`；
  2. 新增 `src/lib/tools.ts`：工具名 → 执行函数（内部复用现有 `callRust`），并做参数校验与结果截断（防超长上下文）；
  3. `chatStream` 增加第二返回值 `toolCalls`，`Assistant.tsx` 或新任务组件循环：调用 → 追加 `tool` 角色消息 → 再请求，直到 `finish_reason = "stop"`。
- 后端兜底（可选，利于性能与安全）：Rust 侧新增 `agent_tool_call` 单一命令，由前端把"工具名 + 参数"交后端执行，避免逐工具新增命令；权限仍走现有命令。

初始工具清单（全部基于已有资产，名称可微调）：

| 工具名 | 作用 | 数据来源 | 现成基础 |
| --- | --- | --- | --- |
| `laws_search(keyword, country?)` | 法条关键词检索（LIMIT 500） | `laws` 表 | ✅ 已有命令 |
| `laws_country_preview(country?)` | 某国重点法规 Top8 | `laws` 表 | ✅ 已有命令 |
| `law_by_id(id)` | 取单条法条全文（供精确引用） | `laws` 表 | 需新增小命令（1 条 SQL） |
| `template_load(category?)` | 载入文书模板 | `templates` 表 | ✅ 已有命令（`templates_list`） |
| `translate_text(text, to)` | 小段翻译 | 翻译引擎 | ✅ `src/lib/translate.ts` |
| `docx_export(json)` | 生成 .docx 交付物 | 新能力 | 参考 `md2docx.py` / 用 `docx` 库或后端模板 |
| `document_save(title, content, file_path)` | 写入"最近文书" | `documents` 表 | 表已建，需补命令 |

### 6.4 可验收交付（docx + documents 表 + 首页）

1. 新增 Rust 命令 `document_save / documents_list / documents_open`，`documents` 表补列（如 `file_path / source_task_id / meta_json`，用兼容迁移方式，参照 `db.rs` 现有 `last_notified_due` 的加列写法）；
2. docx 生成三条路线（按可行性选一）：
   - A. Rust 侧引入 `docx-rs` 等库，`docx_export` 直接产出文件（最稳，单机无依赖）；
   - B. 参考 `法库ETL工作区/md2docx.py`：先让模型产 Markdown，再转 docx（可复用现成脚本逻辑，成本最低）；
   - C. 前端先落 .md/.html 预览 + "另存"再转（演示够用，交付弱）。
   建议 P0 走 **B + A 兜底**，先能"打开文件"。
3. `src/views/Home.tsx` 点亮"最近处理的文书"占位面板，列出 `documents_list`，支持"打开所在文件夹"；
4. 每条引用法条在意见书中带 `篇名 + 条文号 + 来源（e-Gov / govinfo 等）`，与 `laws.source` 列一致——这是可验收性（评委可抽查引用真伪）的关键卖点。

### 6.5 P0 验收清单（每项可现场验证）

- [ ] 输入合同 → 出现计划卡且可编辑；
- [ ] 执行中可见 ≥3 次真实工具调用（日志/进度条可见工具名与耗时），其中至少 2 次为 `laws_search / law_by_id`；
- [ ] 意见书引用法条在本地库真实存在（点"来源"可反查原文）；
- [ ] 一键导出 .docx 且可双击打开，内容与预览一致；
- [ ] 导出后首页"最近文书"出现该条记录；
- [ ] 全程断网可运行（本地库 + 已配置 API 网关），数据不出本机。

## 七、P1：Agent 骨架与工作流状态机

P0 是一条写死的流水线；P1 把它泛化成可复用的 Agent 骨架。

1. **任务数据模型**（后端落 SQLite，参照 `chat_sessions / chat_messages` 风格新增三张表或扩展）：
   - `tasks(id, kind, status, title, plan_json, created_at, updated_at)`
   - `task_steps(id, task_id, seq, name, tool, params_json, status, result_ref, need_confirm)`
   - `task_artifacts(id, task_id, kind, file_path, meta_json)`
2. **流水线模板注册表**（前端常量或后端表）：`审合同 → 意见书`、`起诉状起草 → 文书草稿`、`质证意见 → 三性分析表`；每模板 = 一组"步骤 + 每步工具 + 每步人工确认开关"。
3. **执行引擎**：状态机推进 `planned → running → paused(need_confirm) → done/failed`；支持中断续跑（页面刷新后从 `task_steps` 恢复）。
4. **会话与任务打通**：AI 助手聊天记录关联 `task_id`，可"从任意对话发起任务"；悬浮球划词 → 预填任务输入（复用现有 `ball-push` 桥）。
5. **安全与边界**：工具参数白名单校验、单步超时与最大循环次数（如 15 轮）、异常时暂停并请求人工确认——作为"负责任 AI"设计写入演示话术。

验收口径：任意模板任务可从计划卡开始、自动执行、中途可人工介入、结束后产物入 `task_artifacts` 并可再次打开。

## 八、P2：记忆与检索增强（FTS5 + 向量记忆 + 悬浮球入口）

1. **FTS5 全文索引**（对应 README/路线图自认瓶颈）：
   - `laws` 加 FTS5 影子表（`CREATE VIRTUAL TABLE laws_fts USING fts5(...)`）+ 触发同步或增量 rebuild；
   - `laws_search` 改走 FTS5（BM25 排序）或"FTS 召回 + LIKE 兜底"，目标：15 万条检索从数百 ms～数秒降到毫秒级；这是评委能感知的"技术创新 + 性能提升"实证。
2. **向量记忆（长短期记忆分层）**：
   - 短期 = 会话（已有）；中期 = 案件任务档案（§7）；长期 = 用户自建文档/历史交付物摘要的向量索引；
   - 复用 `src/lib/embed.ts`（已写好未接线）：按任务粒度切片 embedding 存本地向量表（新表 `mem_vectors`），召回用 `cosine()` 内存计算（单机规模足够）；
   - AI 助手提问时先查"任务记忆"，命中则注入"你上次处理过同类案件：……"。
3. **悬浮球升级为任务入口**：划选合同条款 → 弹窗出现"发起合同审查 / 关联法条 / 翻译"三选，联动主应用任务系统（复用 `from-workbench.json` 的 `prefill` 命令扩展 `action`）。
4. **验收口径**：二次发起同类任务时，计划卡/上下文能引用上次交付成果；FTS5 改造后检索耗时量化对比（写入演示报告）。

## 九、P3：多智能体协同（可选冲刺项）

在 P1/P2 之上增加"三角色接力"编排（演示价值高、实现量可控）：

| 角色 | 职责 | 关键工具 |
| --- | --- | --- |
| 检索 Agent（检索员） | 专职法条/历史文书召回，输出候选引用集 | `laws_search / law_by_id / mem 检索` |
| 起草 Agent（文书员） | 按模板与引用集起草文书/意见 | `template_load / docx_export` |
| 质检 Agent（校审员） | 核对引用真伪、口径一致、遗漏风险、格式合规 | `law_by_id` 复核 + 自查清单 LLM 调用 |
| 主控 Agent（主管） | 任务理解、拆步、分发、汇总、冲突裁决 | 规划 + 编排 |

- 实现上可用"一个任务状态机 + 多轮上下文分段"模拟角色间传递（每个角色是独立 system prompt + 专用工具集合），无需引入重型编排框架，保证"给定时间可落地"；
- 汇报中呈现"角色接力过程可视化"（谁在干什么、传了什么给谁），这是工作流编排能力的最直观证据。

## 十、作品创意描述：大模型环节流程（文字版，可直接引用进报名材料）

规则要求创意描述包含**使用大模型的环节流程细节**，建议按下图文字版 + 30–60 s 录屏呈现：

```
① 任务理解        LLM：把用户输入(合同文本+意图) → 结构化任务 JSON
                  输入：用户原文 + 任务模式提示词
                  输出：意图 / 条款分块 / 风险维度 / 检索关键词 / 步骤计划
                  展示：可编辑"计划卡"
        ↓
② 自主规划        LLM：将步骤映射为工具调用序列（含参数与前置条件）
                  展示：执行进度条（每步显示"工具名 + 状态"）
        ↓
③ 工具调用(循环)  LLM 发 tool_calls → 执行层调本地工具
                  · laws_search / law_by_id：真实法条召回（本地 15 万条）
                  · template_load：文书模板
                  · docx_export：成果物生成
                  结果回填 → LLM 决定下一步，直到 finish=stop
                  约束：≤N 轮、异常暂停、每步结果截断、关键步人工确认
        ↓
④ 引用式合成      LLM：按审查模板逐条输出"风险点+修改建议+引用法条(编号+来源)"
                  约束：只允许引用步骤③实际返回的法条，禁止编造
        ↓
⑤ 质量自检        LLM：自查清单（引用是否真实存在、风险维度是否遗漏、口径是否一致）
                  实现：二次调用 + 规则校验（法条号本地可查）
        ↓
⑥ 成果交付        渲染《合同审查意见书》预览 → 导出 .docx → 存入"最近文书"
                  交付物可打开、可溯源、可人工验收
```

配套话术（答辩用）：幻觉防控 = 只引用真实检索结果 + 法条可反查 + 人在环上确认；数据隐私 = 全流程本地库 + 可配置 API 网关；差异化 = 15 万条真实法条开箱即用，竞品多为通用问答或付费云法库。

## 十三、风险与对策

| 风险 | 等级 | 对策 |
| --- | --- | --- |
| 通用模型不支持 `tools`/`json_object`（用户可换网关） | 中 | 工具调用协议做"探测 + 降级"：不支持 tools 时退回"提示词内声明工具清单 + 正则解析动作"，保证演示不翻车 |
